Acceptance of a proven non-list `[1 => 'x', 0 => 'y']`:
`list<string>` rejects ✓; `list{string, string}` **accepts** ✗;
`array{0: string, 1: string}` accepts (correct).
`array_is_list($maybe)` on keyless shape: true branch `array{string,string}`,
false branch `*NEVER*` — i.e. today's "always true".

Observation: written key order leaks into isList today —
`array{1: string, 0: string}` is `No` purely because keys were written in
descending order. Under the key-*set* model it must be Maybe.

## Code map (2.3.x)

- PHPDoc shapes are no longer built in `TypeNodeResolver` directly: they go
  through `LateResolvableArrayShapeType::create()` → `getResult()` (new in
  2.3.x, handles template-typed keys). **This is the single place** where a
  PHPDoc `array{...}` becomes a `ConstantArrayType`, so the denotational
  isList computation for `KIND_ARRAY` belongs there.
- `ConstantArrayType::accepts()` / `isSuperTypeOf()` / `equals()` ignore
  `isList` completely (measured by reading, L524–L970).
- All of `ConstantArrayType`, `ConstantArrayTypeBuilder`,
  `LateResolvableArrayShapeType`, `AccessoryArrayListType`, `TypeCombinator`
  are `#[ShadowedByTurboExtension]` — every PHP change needs the C++ port in
  `turbo-ext/src/*.cpp` + `make bump-turbo` follow-up commit.
- Bleeding edge is read via the static `BleedingEdgeToggle::isBleedingEdge()`
  (C++ side: `ReferencedByTurboExtension(key: 'bleedingEdgeToggle')`).

## Log

### 1. First cut (PHP only)

Changes, all BE-gated unless noted:

- `ConstantArrayType::makeKeyOrderAgnostic()` + private `isListInAnyKeyOrder()`:
  denotational isList over the key *set* (required R, optional O, unsealed
  key type U):
  - No if a required key is a string / negative, or some index below
    `max(R)+1` is neither explicit nor admitted by U;
  - else Maybe if U exists (extras can always add a key) or `|R∪O| ≥ 2`
    (two keys come in either order) or the single key is optional and ≠ 0;
  - else Yes (`array{}`, `array{0: T}`, `array{0?: T}`).
- `LateResolvableArrayShapeType::getResult()`: for `KIND_ARRAY` /
  `KIND_NON_EMPTY_ARRAY` call `makeKeyOrderAgnostic()` on the built shape.
  Single entry point for PHPDoc shapes on 2.3.x — no TypeNodeResolver change.
- `accepts()` / `isSuperTypeOf()`: `isListRequired()` = BE ∧ isList yes ∧
  key set alone does *not* make it a list. Then the other side's `isList()`
  is and-ed in (with a 💡 reason on accepts). Excluding the "key set settles
  it" case keeps `array{0: T}` / `array{}` from producing noise reasons.
- `equals()`: compares isList. Needed because `TypeCombinator::union()` has
  an `$a->equals($b) && isArray` fast path (L293) that otherwise keeps
  whichever of `list{s,s}` / `array{s,s}` came first.
- `shouldBeDescribedAsAList()`: under BE = isList yes ∧ key set alone does
  not make it a list. This is exactly the RFC's "round-trip faithfulness"
  rule and — unlike the RFC's "every yes-list" wording — keeps
  `array{}`, `array{string}`, `array{0?: string}` spelled as `array`, which
  cuts churn. RFC text should be read as this (the principle, not the
  shorthand).
- `tryRemove()`: removing a type that covers `$this->makeList()` from a
  Maybe shape flips isList to No (`array_is_list()` false branch).

Probe after first cut: every row of the baseline table now matches the RFC
target; `list{string, string}` rejects `[1 => 'x', 0 => 'y']` and a Maybe
`array{string, string}` ("expects list{string, string}, array{string, string}
given").

### 2. Bugs found by probing the first cut

- **Union collapsed to the list**: `list{s,s}|array{s,s}` → `list{s,s}`.
  Cause: `mergeWith()` / `legacyMergeWith()` do
  `$naiveIsList->or(inferIsListFromShape(...))` (from #6025), and
  `inferIsListFromShape()` reads the *declared* key order, so Maybe ∨ Yes =
  Yes. Fix: new `inferIsListFromMergedShape()` caps the inferred value at
  Maybe under BE (`->and(Maybe)`). Yes still comes from two list inputs via
  `$naiveIsList`, which is what #6025's "or keeps a genuine yes" comment was
  about. No new yes()/no() call → no new TrinaryLogicMutator surface.
- **makeList() too weak**: `array{1: int, 0?: string}` ∧ list gave
  `array{0?: string, 1: int}` (still Maybe, still optional 0). Fixed
  (unconditionally — pure precision fix, stable too): keys below the highest
  required index become required, keys are rebuilt ascending, and the rebuilt
  shape is marked Yes explicitly (the builder alone answers Maybe for an
  optional tail like `[0, 1?, 2?]`).
- Key order matters for positional ops even under the new model: a list is
  the one case where the order is known, so `makeList()` must put keys in
  ascending order (`array{1: int, 0: string}` ∧ list → `list{string, int}`,
  and `array_values()` of it is then correct).

### 3. Full suite on the first cut: 204 failures → triage

Measured with a junit classifier (scratchpad `classify.py`):
674 NSRT asserts pure `array{`→`list{` churn, 28 union-member reorders
(`array{` sorts before `list{`), ~55 rule tests (mostly message churn),
and a small set of real semantic diffs. The RFC predicted "~half of 1,900
array{ asserts" — actual churn is **~700 asserts** because the round-trip
rule keeps `array{}`, `array{T}`, `array{0?: T}` spelled `array`.

Real issues surfaced by the suite (each fixed):

- **Count narrowing lost** on `array{0: mixed, 1?: string|null}` (now Maybe):
  `CountNarrowingHelper` only reconstructs shapes when `isList()->yes()`
  (`truncateListToSize`). Under the key-*set* model a size only pins the
  optional keys at the two extremes (none / all) — `array{0: a, 1?: b, 2?: c}`
  with count 2 is `{0,1}` *or* `{0,2}`. New `narrowConstantArrayToSize()`
  picks the `getAllArrays()` variant for exactly those two sizes. Side
  effect: a precision *gain* for non-list shapes too
  (`array{a: int, b?: string}` + `count === 1` → `array{a: int}`), 5 NSRT
  expectations tightened (list-count, equality-narrowing-new-world).
- **`getAllArrays()` re-derived list-ness from declared order**: every
  variant goes through the builder, so the `{0,1}` variant of a Maybe shape
  came back Yes. Under BE the variants of a non-list keep the parent's
  semantics (Maybe → `makeKeyOrderAgnostic()`, No → No).
- **Loop non-convergence (bug-13786)** once `equals()` compares isList:
  `non-empty-array{a?: '0', b?: '0', c?: '0'}` has two representations —
  CAT(No)&non-empty from the builder, CAT(Maybe)&non-empty from `mergeWith()`
  (which lifts because the *bare* merged CAT admits `[]`). Loop fixpoint uses
  `equals()` → never converges → generalized to `non-empty-array<'a'|..., '0'>`.
  Root cause pre-dates this work (#6025's lift); it was masked because
  `equals()` ignored isList. Fix: canonicalize in `TypeCombinator::intersect`
  — a Maybe CAT that cannot have key 0 is No once intersected with
  non-empty-array ("every non-empty list has the key 0"). Must run *after*
  the existing "single optional key + non-empty → required" rule or it
  short-circuits it (array-shape-from-general-array-with-single-finite-key
  regressed until reordered).
  - Why not make `equals()` compare only `isList->yes()`? Scope merging
    (`ExpressionTypeHolder::and`) keeps `$this` when `equals()` — a Maybe vs
    No (after `array_is_list()` false branch) merge could then keep No and
    report "always false". Full isList comparison is needed for soundness.
- **Lost `non-empty` on template-keyed shapes**: the builder returns
  `CAT & non-empty-array` for a union key; unwrapping via
  `getConstantArrays()[0]` dropped the accessory. Re-added it.
- **`describe()` at typeOnly printed `list<int, X>`** (invalid syntax) once
  Yes-lists render as `list`; now `list<X>`. Also affects the pre-existing
  optional-key `list{...}` rendering on stable (was latent).
- `bug-14177` line 187 `bool` → `false`: precision gain from the stronger
  `makeList()` (`list{0: s, 1?: s, 2?: s, 3: s}` really requires 1 and 2).

Intended semantic changes that needed expectation updates:
- `array-is-list-type-specifying` foo3: false branch of `array_is_list()`
  on a union of keyless shapes is no longer `*NEVER*` (the other key orders).
- `array-is-list-offset`: PHPDoc switched to `list{bool, bool, bool}` to keep
  the test about offset writes on a list.
- `TypeToPhpDocNodeTest` #39/#41: fixtures built with the constructor
  default (`isList` null → **No** for non-empty keys) are the non-denotable
  "reversed order only" residue; `array{'foo', 'bar'}` now parses back to
  Maybe. Fixtures pass `isList: Maybe`.

### 4. Open design question: constructor default

`new ConstantArrayType([0, 1], ...)` without `$isList` is **No**. Under the
old model that meant "not a list" (so `list<T>` already rejected it); under
the new model a No-flag CAT with keys {0,1} denotes only the reversed order.
Extensions constructing sequential shapes without `makeList()` now also fail
`list{...}` acceptance. A principled BE default would be
`isListInAnyKeyOrder()` (order unknown). Not changed yet — would widen the
blast radius (many internal `new ConstantArrayType(...)` rely on No); worth
raising upstream.

### 8. Open questions to raise upstream

1. **Constructor default** (§4): BE default for `$isList === null` — keep No
   or switch to `isListInAnyKeyOrder()`?
2. **Canonical key order for equals()** (audit C2): `array{1: T, 0: U}` and
   `array{0: U, 1: T}` are still unequal (positional key comparison). Not
   needed for soundness here (isSuperTypeOf is order-insensitive, unions
   collapse them), left out to avoid more churn.
3. **Positional projections** (RFC §"not proposed"): `array_values()` etc.
   still trust declared order of a Maybe shape — `array_values(array{1: int,
   0: string})` gives `list{int, string}` although the list could be
   `[string, int]`. Unchanged by design; #14940 tracks the family.
4. The `non-empty` canonicalization rule (Maybe CAT without possible key 0
   ∧ non-empty ⇒ No) lives in TypeCombinator::intersect; an alternative is
   teaching `mergeWith()` about accessories. Current choice is the smallest
   that makes the loop converge.
5. RFC wording "describe() renders yes-lists as `list{...}`" should be
   refined to "…whenever `array{...}` would not read back as always-a-list"
   (keeps `array{}`, `array{T}`, `array{0?: T}`), halving the churn estimate.

### 9. PR description draft (not posted — needs explicit approval)

Title: `Tell array shapes from list shapes by the key orders they admit`

Body (GitHub: one paragraph per line):

```
Implements the model agreed in phpstan/phpstan#14939 on bleeding edge: `array{...}` describes a set of keys that may come in any order, `list{...}` (or `...&list`) additionally promises them in ascending order.

- A PHPDoc `array{...}` gets the `isList()` its key set implies: `array{string, string}` / `array{0: string, 1: string}` are maybe-lists, `array{}`, `array{0: T}`, `array{0?: T}` are always lists, `array{a: T}` / `array{1: T}` never are.
- A list shape only accepts (and is only a supertype of) a list, with a tip: "A list shape only accepts a list: its keys must be 0..n-1 in ascending order."
- `equals()` tells `list{T, U}` from `array{T, U}`; `describe()` spells a list `list{...}` whenever `array{...}` would not read back as always-a-list.
- `array_is_list()` narrows both ways: the true branch rebuilds the keys in ascending order (making keys below a required one required), the false branch keeps the other key orders.
- `getAllArrays()` and shape merging no longer read list-ness off the declared key order; a non-empty shape that can never have the key 0 is canonically not a list (keeps loop fixpoints converging, bug-13786).
- `count()` narrows a non-list shape to none/all of its optional keys when the size pins them.

Outside bleeding edge only `makeList()` gets stronger and a list reads `list<T>` instead of `list<int, T>` at type-only verbosity.

About 700 NSRT assertions change from `array{...}` to `list{...}` (pure rendering); the semantic expectation changes are listed in the commit.

The native mirrors in turbo-ext are updated in the same commit; `tests/type-family.php` gains a bleeding-edge block covering the new paths (PHP and native agree on all observations).

Closes https://github.com/phpstan/phpstan/issues/12725
```

### 12. Trade-offs surfaced by the implementation

Measured with `probe/levels.php`, `probe/tradeoff.php`:

1. **Positional projections now contradict `isList()` visibly.**
   `array{int, string}`: `array_is_list()` → bool, but `array_values()` →
   `list{int, string}` and `takesIntString(...$a)` passes; runtime may be
   `[1 => 's', 0 => 5]`. Before, both were "consistently" order-trusting.
   `array_key_first/last`, `reset/end`, `array_pop/shift`, foreach are sound
   unions. Options: accept (RFC), permutation-union (precision loss),
   document. Migration to `list{...}` makes these both precise and sound.
2. **New errors land at level 7** (maybe-acceptance) for `array{...}` →
   `list<T>`/`list{...}`/list template bounds/`@var` downgrades; proven
   non-lists (`[1 => …, 0 => …]` → `list{…}`) at level 5. Tips:
   list shape → "A list shape only accepts a list …"; `list<T>` → existing
   "X might not be a list." (no migration hint there).
3. **Baselines**: messages containing `array{...}` change to `list{...}`
   (~700 in phpstan-src tests); with `rawMessageInBaseline` users' baseline
   entries stop matching when enabling BE → resurfaced + unmatched ignores.
   Same class of cost as the sealed-shapes rollout, should be announced.
4. **Non-denotable No residue** (false branch of `array_is_list()`): prints
   like the Maybe shape at precise level (`array{string, int}`); only the
   cache level distinguishes. Also imprecise key structure:
   `array{0: string, 1?: int}` false branch keeps `1?` → `count()` =
   `int<1, 2>` though it must be 2 (sound, refinable later).
5. **Count narrowing only at the extremes** for non-list shapes:
   `array{0: s, 1?: s, 2?: s}` + `count === 2` is not narrowed any more
   (was a prefix under list semantics) — inherent to key-set semantics;
   `list{...}` keeps prefix narrowing.
6. **Constructor default** `$isList = null` → No: sequential-key CATs built
   by extensions without isList mean "reversed only"; now also distinct from
   PHPDoc Maybe in equals()/cache keys (`array{a?: int}&isList(No)` observed
   in type-family). Open question for upstream.
7. **`equals()` strictness can expose other Maybe/No double
   representations** (one found and fixed: non-empty). Risk = loop
   non-convergence → generalization in user code not covered by tests.
   Mitigation: analyse a few real projects under BE, compare timing/errors.
8. **`list{T}` written by the user prints as `array{T}`** (and `list{}` as
   `array{}`) because the key set already makes it a list — correct (equal
   types) but may surprise.
9. **Every future change to array-shape semantics needs the C++ port**
   (ConstantArrayType, TypeCombinator, LateResolvable, CountNarrowingHelper
   are shadowed on 2.3.x); the cache-level suffix is a new describe format
   both sides must keep identical.
