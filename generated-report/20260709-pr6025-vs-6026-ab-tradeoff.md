# PR #6025 vs #6026 — 無効な sealed list-shape 射影の A/B トレードオフ

[phpstan/phpstan#14938](https://github.com/phpstan/phpstan/issues/14938)
（optional な非list互換キーが `isList` を No にしてしまう）に対して、
2つの PR が並行して提出された際の議論の記録と、最終的な立場表明。

- **#6025**（zonuexe / 本セッション）: https://github.com/phpstan/phpstan-src/pull/6025
- **#6026**（phpstan-bot）: https://github.com/phpstan/phpstan-src/pull/6026
- トレードオフ提示コメント: https://github.com/phpstan/phpstan-src/pull/6026#issuecomment-4918140624

## 経緯の要約

1. #14938 を起票（本セッションの型理論監査の副産物）。
2. #6025 を実装・提出。修正は当初想定の1層でなく **3層** 必要だった：
   - `ConstantArrayTypeBuilder::markNonListKey()` — optional キーは Yes→Maybe 格下げ（No は据置）
   - `ArrayType::isSuperTypeOf()` — 空になりうる constant array は `[]` を含むので No→Maybe
   - `ConstantArrayType::makeList()` — sealed な Maybe-list の `list` 交差で連続 `0..m` プレフィックスへ射影
3. phpstan-bot が #6026 を自動提出。分析の結果：
   - `ArrayType` 変更は **完全一致**（`isConstantArray()->yes()` の使い方まで）
   - Builder 変更は等価（bot は inline、こちらはヘルパ）
   - bot は **merge 側の同族バグ**（`mergeWith`/`legacyMergeWith`）も修正しており、こちらは見落としていた
   - bot は `makeList()` を触っておらず、無効キーを **保持** する
4. merge 修正＋`inferIsListFromShape()`（2,929 形状のブルートフォース照合済み）を
   #6025 に取り込み（fixup `7f213cad5`）、帰属を
   [コメントで明記](https://github.com/phpstan/phpstan-src/pull/6025#issuecomment-4918221485)。
5. 残る唯一の分岐が本稿の A/B。#6026 にトレードオフを提示し、メンテナの選択に委ねた。

## A/B の定義

sealed な shape に「list では絶対に出現できない optional キー」（gap の先の int キー、
文字列キー）が含まれるとき、`list` との交差（`makeList()`）をどう解決するか。

**案 A — 死んだキーを保持（#6026）**

```
list{0: string, 1: int, 2?: string, 4?: string}   // 4? が gap(3) の先に残る
array{a?: string} & list  →  list&list{a?: string} // list 上に死んだ a? が残る
```

**案 B — 到達不能キーを削除（#6025 の makeList 射影）**

```
list{0: string, 1: int, 2?: string, 4?: string}  →  list{0: string, 1: int, 2?: string}
array{a?: string} & list  →  list{}
```

## トレードオフ詳細

| 観点 | A（保持） | B（削除） |
|---|---|---|
| 実装 | 1行相当・追加コードなし | `makeList()` に射影ステップ（〜30行） |
| 型の well-formed 性 | ✗ 存在不能なキーが型に残る | ✓ 全キーが実現可能 |
| offset アクセス | ✗ `$x[4]` が `string`（maybe-exists）と推論される — 実際には**絶対に存在しない** | ✓ `$x[4]` は undefined offset として報告 |
| `count()` | ✗ `array{a?: string}&list` の count が 0..1 と推論されうる（真値は 0） | ✓ `list{}` の count は正確に 0 |
| 外延的意味論 | 型の denotation は同じ（optional キーは「無いかもしれない」）だが、**キー構造が denotation を過大表示** | denotation と構造が一致 |
| 診断メッセージ | 元 PHPDoc の痕跡（`4?: string`）が残るので、**書き手のタイポに気付きやすい**可能性 | 痕跡が消える（ただし本来は無効 shape を lint するルールの仕事） |
| describe の一貫性 | `list&list{a?: string}` のような交差表示が漏れる | `list{}` に正規化 |
| 先例との整合 | — | 修正前の挙動も `*NEVER*` への「射影」（過剰版）だった。B はそれを外延的に正しい射影に置き換えるだけで、「交差時に shape を変形する」前例は既にあった |

### B を支持する核心の論拠

`list` と交差した後の型は「list である値の集合」を表す。その集合のどの要素にも
キー `4` や `'a'` は**存在しない**。存在しないキーを optional として型に残すのは、
`isList` バグと同型の誤り——「型のメタデータが denotation を過大／過小表示する」——を
別の場所（キー構造）で再生産することになる。#14938 の修正の精神を一貫させるなら、
交差結果のキー構造も denotation に忠実であるべき。

具体的な実害の差：A では narrowing 後に `$x['a']` へアクセスするコードが
「maybe string」として通りうるが、実行時にその分岐に入った時点で `'a'` は
決して存在しない。B なら静的に undefined offset として検出できる。

### A を選ぶ場合の正当化（公平のために）

- 変更が最小で、`makeList()` の再帰的な builder 呼び出しという新規コードパスを持ち込まない。
- 「無効な list-shape を書いた」のはユーザーの PHPDoc 側の問題であり、型エンジンが
  静かに射影するより、痕跡を残す（将来的には専用ルールで警告する）方が親切、という立場もありうる。
- bot PR（キュレートされた自動修正）が A を選んだこと自体が、保守側の
  「最小差分」嗜好のシグナルかもしれない。

## 最終的な立場

**B を支持する。**

1. 型は denotation（取りうる値の集合）に忠実であるべきで、到達不能キーの保持は
   #14938 と同族の「メタデータと denotation の乖離」を残す。
2. offset アクセス・count の健全性で実測可能な差が出る（A は false-valid を生む）。
3. コストは `makeList()` 内の局所的な射影のみで、全テスト
   （nsrt+Type 4,648 / 受理系 Rules 847 / legacy 等 267）がクリーン。
4. 「痕跡を残して気付かせる」役割は、型構造ではなく無効 list-shape を検出する
   PhpDoc ルール（将来課題、RFC #14939 の周辺）が担うのが筋。

なお、メンテナが A（#6026 ベース）を選んだ場合も merge 修正は共通なので実害は小さく、
`makeList()` 射影は後続 PR として独立提案できる。**どちらがマージされても
#14938 は閉じる**構図にしてある（両 PR に相互参照コメント済み）。
