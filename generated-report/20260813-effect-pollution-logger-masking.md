# システムワイドなロガーと効果の汚染: 正直な報告・便宜的隠蔽・宣言されたマスキング

v0.1.5 リリース前の private corpus 実測(数字と固有名は репо 外に置く)が
持ち込んだ問いの記録。効果システムが全プログラム伝播で正直であるほど、
横断的関心事(ロガー)が purity を絶滅させる — この緊張を三択として定式化し、
前例文献に接地して設計方向を書き留める。

## 0. 発端(抽象化して)

大規模 private コードベースで、クラス単位 pure 宣言
(`@phpstan-all-methods-pure`)のメソッド群が数千件の
`effect.envelope-exceeded` を生んだ。経路は一様で:

```
pure 宣言クラス → 検証/assert ヘルパ → デバッグロガー → 時計・FS
```

決定的な観察: そのコードベース自身が、ロガー呼び出しの直前に
`// @phpstan-ignore impure.methodCall` を書いていた。つまり
**PHPStan もそこを不純と判定しており、作者は承知の上で黙らせている**。
モジュラな PHPStan は ignore された地点で止まり、全プログラム伝播の
Steins は効果を果てまで運んで宣言に突き当てる。

ここから出る新しい教訓: **ignore は報告の抑制であって、効果の discharge
ではない**。呼び出し箇所の ignore は「この行を黙らせる」だけで、効果は
伝播し続ける。抑制と放電を区別する語彙を、共有仕様はまだ持っていない。

## 1. 三択の定式化

1. **正直な全報告** — 意味論的には正しい。ロガーが `nondet.time` と
   `io.fs.write` に到達する事実は事実である。しかしシステムワイドな
   ロガーに(推移的に)触れる全経路で purity が達成不能になり、数千件の
   「真だが行動不能」な報告が生まれる。効果の汚染 (effect pollution)。
2. **便宜的隠蔽** — カタログや宣言で「ロガーは pure」と嘘をつく。
   このプロジェクトが繰り返し拒否してきた metadata の嘘そのものであり、
   「どこが時計に触るか」という監査の問いにも答えられなくなる。却下。
3. **宣言されたマスキング** — 嘘をつかず、隠蔽を「名前のある・監査可能な・
   検査可能な」一級の操作にする。以下はこの路線の設計素描。

## 2. (3) の理論的正体: 観測的純粋性と良性副作用

- **Haskell の `Debug.Trace.trace`** — `unsafePerformIO` 経由のログ出力を
  「良性 (benign)」としてコミュニティが公認してきた、実務上の先例。
  型は純粋、実体は出力。まさに「便宜的隠蔽を一箇所に閉じ込めた」形。
- **観測的純粋性 (observational purity)** — 仕様検証の文献では、キャッシュ・
  メモ化・ログのような「プログラムの観測可能な振る舞いに影響しない副作用」を
  仕様レベルで純粋と扱う系譜がある(Barnett–Naumann らの observational
  purity / "99.44% pure" の系統、JML/Spec# の pure メソッド議論)。
- **Koka `mask` / Flix の cast** — 効果を型から消す操作は既存効果システムに
  もあるが、**明示の構文**であって既定ではない
  ([Koka `mask`](https://dl.acm.org/doi/10.1145/3093333.3009872)、
  Flix の checked/unchecked cast)。
- **`mutate.local` の前例** — Steins は既に「全 envelope が許容する退化
  メンバ」を一つ持っている。根拠は「呼び出し元から観測不能」。ログはその
  弱い親戚で、**プログラム自身からは**ほぼ観測不能(戻り値を消費しない
  fire-and-forget、制御フローが依存しない)だが、**世界からは**観測可能
  (ファイルは育つ)。だから mutate.local と同格には昇格できない —
  「誰にとって観測不能か」という軸が要る。

## 3. 設計方向(提案、未裁定)

**許容集合の政策化。** `mutate.local` の「全 envelope が許容」という機構を
一般化し、policy profile が宣言できるようにする:

```toml
[profile.app]
extends = "contracts"
tolerated-effects = ["telemetry"]   # pure envelope の検査から差し引く
```

この形が守る三性質:

1. **カタログは嘘をつかない** — `time()` は `nondet.time` のまま。証明
   レーンは完全に正直で、annotate は全効果を見せ続ける。
2. **隠蔽は名前付きで監査可能** — 差し引きは profile に列挙され、diff に
   出る。call site に散る ignore と違い、一箇所で政策として読める。
3. **問いごとに可逆** — 「どこが時計に触るか」という監査はラベルが残って
   いるので答えられる。envelope 検査だけが許容する。

**意味ラベルとの合成。** ロガーのファサードに plugin(ADR-0068 channel)が
`telemetry.log` を重ね、政策は transport(`io.fs.write`/`nondet.time`)
ではなく**意味ラベル**を許容する。同じ `time()` でも「ログの時刻印」と
「ロジックの時刻依存」が区別でき、後者は許容されない — 隠蔽の粒度が
「何をしたか」でなく「何のためにしたか」に揃う。

**AOP / 注入されたログ。** 織り込みで挿入される呼び出しは作者の意味論では
ない。ならばマスクを宣言すべき当事者は**注入者**(フレームワーク plugin)
であって各 call site ではない — plugin が意味ラベルの付与と政策許容の推奨を
同時に出荷する、という分業が ADR-0068 の既存機構にそのまま載る。

**throw 経路限定の効果(観察のみ)。** assert ヘルパのログは失敗経路にだけ
ある。Koka の pure = ⟨exn,div⟩(投げることは pure と両立)に照らせば、
「throw で終わる経路上の効果は例外の荷物」と見なす路線も考えうる。
経路感応の効果は大工事なので、open question として記録に留める。

## 4. 共通仕様への含意

`-except`(steins#312)・`@phpstan-masks` 系(ob_start マスキング)・本件の
政策許容は同じ家族 — **bound から差し引く操作の三形態**(語彙で・HOF で・
政策で)である。upstream 議論に持ち込むなら、一番伝わる切り口は
「**ignore と discharge の区別**」: PHPStan 利用者が今日 ignore で表現して
いる「ここが不純なのは承知」は、報告の抑制であって効果の放電ではなく、
全プログラム伝播の下では別の場所に再出現する。放電を一級にする構文/政策が
あれば、その ignore は意図を運ぶ宣言に変わる。
