# PHPStan 2.2.x → 2.3.x: 副作用処理の差分調査

調査日: 2026-09-15

## 結論

変化はある。ただし、`@phpstan-pure` / `@phpstan-impure` や
`hasSideEffects()` の公開契約が変わったのではない。確認できた実質的な差は次の二系統である。

1. 2.3.x は、static method / static closure が到達できる状態を区別して、
   call 後に忘れる型事実を狭くした。receiver を渡していない static call では
   `$this->property` 等を保持する一方、object / resource を引数として渡した場合は
   その引数に結び付く事実を無効化する。
2. 2.3.x の single-pass expression engine は、同じ式の中で先に起きた代入等を
   後続の引数・配列要素・generic acceptor 選択へ反映する。

一方、effect label、`@phpstan-impure io` の意味解釈、新しい effect vocabulary、
builtin の `hasSideEffects` 再分類は upstream 2.3.x に入っていない。
2.3.x 内には purity / impure point 関連の commit が複数あるが、その多くは
single-pass 化の途中で 2.2.x 相当の意味を復元した修正であり、最終 tip 同士の仕様差ではない。

## 比較点と方法

2026-09-15 に `phpstan` remote を fetch し、次を比較した。

| branch | commit | subject |
|---|---|---|
| 2.2.x | [`76f47ddb8`](https://github.com/phpstan/phpstan-src/commit/76f47ddb80b854e7e435b282409ea0c52204dfd7) | Remove the PHP version constraint from the `#[\\NoDiscard]` attribute rules. |
| 2.3.x | [`77841303f`](https://github.com/phpstan/phpstan-src/commit/77841303f2b8174c6d22309d8e89f2436b746f86) | Merge branch 2.2.x into 2.3.x |

`git merge-base` は 2.2.x tip の `76f47ddb8`。`git rev-list --left-right --count`
は `0 255` だった。したがって、この比較では 2.3.x が最新 2.2.x をすべて含み、
その上に 255 commit ある。

調査は次の順で行った。

- `hasSideEffects`, `ImpurePoint`, `PossiblyImpureCallExpr`, `isPure`,
  `rememberPossiblyImpureFunctionValues`, `pureUnlessCallable`,
  `invalidateExpression` を pickaxe して 2.3.x 固有 commit を抽出。
- PHPDoc resolver、purity rules、`SimpleImpurePoint`、builtin metadata、設定値の
  blob / diff を比較。
- 両 tip の detached worktree を作成し、同じ PHP 8.5.10 と dependency tree で
  targeted PHPUnit を実行。2.3.x の新規 NSRT fixture は 2.2.x 側にもコピーして、
  同じ期待値を満たすかを differential probe として確認した。

最後の probe は 2.2.x 自身の回帰テストではない。2.3.x が保護している挙動を
2.2.x engine が同じように示すかを測るための比較である。

## 1. 公開の purity / effect 契約は変わっていない

次の effect 中核ファイルは両 branch で blob hash が一致した。

| `src/Reflection/Callables/SimpleImpurePoint.php` | `95067a613805` |

このため、少なくとも次は 2.2.x と 2.3.x で同じである。

## 2. 実挙動差: static call の effect footprint が到達可能性に応じて選択的になった

中心 commit は [`b48812e11`](https://github.com/phpstan/phpstan-src/commit/b48812e116451ae7492ac18214807df407966df3)
`Keep property fetches on the receiver when a static method or static closure invalidates it (#6391)`。

2.2.x は impure な static method / static closure の後で receiver に根を持つ型事実を
広く捨てた。2.3.x は `MutatingScope::invalidateExpression()` と `ScopeOps` に
`keepPropertyFetches` を通し、callee が receiver を受け取らない経路では property chain を残す。
実装は [static closure の reachability 判定](https://github.com/phpstan/phpstan-src/blob/77841303f2b8174c6d22309d8e89f2436b746f86/src/Analyser/ExprHandler/Helper/FuncCallScopeEffectsHelper.php#L103-L127) と
[`ScopeOps::shouldInvalidateExpression()` の carve-out](https://github.com/phpstan/phpstan-src/blob/77841303f2b8174c6d22309d8e89f2436b746f86/src/Analyser/ScopeOps.php#L862-L896)
にある。

代表例は `tests/PHPStan/Analyser/nsrt/bug-13735.php` と `bug-13735b.php`。

```php
$this->foo = new Foo();
self::sideEffect(); // static。receiver は引数にない
assertType(Foo::class, $this->foo);
```

同じ 2.3.x fixture を 2.2.x で走らせると、2.2.x は call 後を `Foo|null`、
2.3.x は `Foo` とした。nested / nullsafe property chain、array-valued property の
offset fact、static method を instance syntax で呼んだ場合、capture のない static closure
でも同じ方向の差を確認した。

これは単なる「忘れない」変更ではない。2.3.x は static closure に渡された object / resource を
明示的に無効化する [`invalidateObjectArgs()`](https://github.com/phpstan/phpstan-src/blob/77841303f2b8174c6d22309d8e89f2436b746f86/src/Analyser/ExprHandler/Helper/FuncCallScopeEffectsHelper.php#L395-L425)
も追加した。

```php
if (ftell($fh) !== false) {
    $staticClosure = static function ($handle): void {
        fseek($handle, 10);
    };
    $staticClosure($fh);
    assertType('int|false', ftell($fh));
}
```

この probe では 2.2.x が最後の `ftell($fh)` を `int` のまま保持し、2.3.x は
`int|false` に戻した。2.3.x は、無関係な receiver state を保持するだけでなく、
callee に実際に渡した mutable state は忘れる。effect の「有無」ではなく、
到達可能な object / resource を footprint として扱う方向の改善である。

### 残る不健全性

upstream test 自身が、static property 経由の alias は追跡しないと明記している。

```php
self::$instance = $this;
$this->foo = new Foo();
self::mutateStored(); // self::$instance->foo = null にできる
assertType(Foo::class, $this->foo); // 2.3.x も Foo を保持
```

したがって `keepPropertyFetches` は完全な effect / alias analysis ではない。
「static method は `$this` を直接受け取らない」という局所近似であり、static state に保存した
receiver までは footprint に戻せない。この制限は effect label を追加しても自動では解消しない。

## 3. 実挙動差: 式内の state mutation を左から右へ反映する

2.3.x の大きな内部変更は、expression を繰り返し値付けする構造から、歩いた結果を
`ExpressionResult` / `ArgsResult` に保持する single-pass 構造への移行である。
call handler は、各引数を変化していく scope 上で処理し、その後に resolved acceptor、
return type、impure point を決める。

[`63d33d6ab`](https://github.com/phpstan/phpstan-src/commit/63d33d6abe89515ee19a82b302a0ee1fc968a14b)
`Rework the call handlers around preliminary results and ArgsResult` の probe:

```php
/**
 * @template T of object
 * @param mixed $foo
 * @param T $in
 * @return T
 */
function doFoo($foo, object $in): object
{
    return $in;
}

$r = doFoo($a = new stdClass(), $a);
assertType(stdClass::class, $r);
```

2.2.x は `$r` を `object`、2.3.x は `stdClass` とした。第 1 引数の代入 effect が
第 2 引数を読む時点まで反映され、generic `T` の解決に使われる。

配列リテラル内の連続する代入・読み取り・increment でも差が出た。

```php
$a = [
    $b = 1,
    $b + 1,
    $c = $b,
    $c + 2,
    $c++,
    $c,
];
```

2.3.x は `array{1, 2, 1, 3, 1, 2}`、2.2.x は
`array{1, (float|int), *ERROR*, (float|int), *ERROR*, *ERROR*}` だった。
これは `@phpstan-impure` の意味変更ではないが、「式の評価が scope に及ぼす効果」を
次の sub-expression へ渡す精度は明確に変わっている。

### impure point の生成位置

2.3.x では method / static call / constructor の impure point を引数処理後に作るようにした。
例えば [MethodCallHandler 157-184 行](https://github.com/phpstan/phpstan-src/blob/77841303f2b8174c6d22309d8e89f2436b746f86/src/Analyser/ExprHandler/MethodCallHandler.php#L157-L184)
は `ArgumentsHandler::processArgs()` の後で
`SimpleImpurePoint::createFromVariant()` を呼ぶ。理由は
`@pure-unless-callable-is-impure` が callback 引数の処理済み型を必要とするためである。

関連 commit:

- [`ca196e010`](https://github.com/phpstan/phpstan-src/commit/ca196e0104763c77c48141c66ea9435a11e2f03a): method / static call。
- [`078fe8c9c`](https://github.com/phpstan/phpstan-src/commit/078fe8c9cf18accd39bacce07002687d54c34e6a): constructor。

ただし、NSRT `param-pure-unless-callable-is-impure.php` は両 tip で pass した。
したがって、生成位置の変更は 2.3.x の storage model に必要な port であって、
pure-unless の公開意味を 2.2.x から変えたものではない。

## 4. 2.3.x の commit だが、tip 間の意味変更ではないもの

次の fixture を 2.2.x と 2.3.x の双方で実行したところ、両方 pass した。

- `impure-call-asserts-not-remembered.php`
- `impure-nullsafe-call-not-remembered.php`
- `nullsafe-impure-call-narrowing.php`
- `narrowing-leaks-composition.php`
- `indexed-assign-rhs-container-mutation.php`
- `arrow-function-call-arg-type.php`
- `nullsafe-receiver-closure-arg.php`

特に [`3b57b6ba4`](https://github.com/phpstan/phpstan-src/commit/3b57b6ba40b0e2ff351139a28f7b2208a47adecd) と
[`bc36ada2d`](https://github.com/phpstan/phpstan-src/commit/bc36ada2d4b0319e26f4c8faa20bd4fd8267e847)
は、`@phpstan-assert*` を持つ impure call や nullsafe impure call の truthiness を
記憶しないよう修正している。しかし commit message 自身が 2.2.x の旧
`TypeSpecifier::create()` gate と同じにする修正だと説明しており、differential probe も
最終 2.2.x がすでに同じ挙動であることを確認した。

同様に [`194bd0e22`](https://github.com/phpstan/phpstan-src/commit/194bd0e22ed61c8c4bc61553a48c6140ade867f4)
`Use template bounds for objects passed to impure mixed parameters` も、
最終 fixture では pure / impure な mixed consumer の双方が両 tip で同じ型になり、
branch 間の purity 契約差としては数えなかった。

## 5. effect-envelope branch への含意

### 5.1 2.3.x 用 port の seam は変わった

2.2.x の `NodeScopeResolver` 中心の hook をそのまま移すのは不十分である。
2.3.x では少なくとも次の分担に合わせる必要がある。

- call-site effect の生成: `ExprHandler/FuncCallHandler`, `MethodCallHandler`,
  `StaticCallHandler`, `NewHandler`。
- 引数依存 effect の判定: `ArgumentsHandler::processArgs()` 後の `ArgsResult` と post-arg scope。
- call 後の state invalidation: `FuncCallScopeEffectsHelper`, 各 call handler、
  `MutatingScope::invalidateExpression()`, `ScopeOps`。
- value remembering / narrowing: `ExpressionResult` と
  `DefaultNarrowingHelper` 側の purity gate。

### 5.2 label と invalidation footprint を同一視しない

`b48812e11` は、同じ「impure call」でも

- receiver を受け取らない static call、
- object / resource を引数に受け取る static closure、
- receiver を capture / alias し得る closure

で忘れるべき型事実が違うことを示す。`io.fs.write` や `mutate` のラベル集合だけでは
どの expression を無効化するかは決まらない。effect kind と reachability / alias footprint は
別レーンにして、boolean `hasSideEffects` の置き換え時にも invalidation 情報を失わない方がよい。

### 5.3 最低限追加すべき port regression

effect-envelope branch の 2.3.x port では次を固定したい。

1. `@phpstan-impure <label>` な static method を receiver なしで呼んでも、
   無関係な `$this->property` の型を落とさない。
2. static closure / static method に object または resource を渡したら、
   その引数に依存する remembered call value / property fact を落とす。
3. 第 1 引数の代入や callback construction が、第 2 引数に依存する dynamic effect 判定へ
   左から右の順で反映される。
4. `@phpstan-impure` + `@phpstan-assert*`、nullsafe impure call の値を記憶しない。
5. `rememberPossiblyImpureFunctionValues: false` でも同じ effect-envelope containment を保つ。

```text
  PureFunctionRuleTest + PureMethodRuleTest       27/27 pass
  DoNotRememberPossiblyImpureFunctionValuesTest  20/20 pass

```

2.2.x の 6 failures のうち、このレポートで side-effect delta として採用したのは
`bug-13735.php`, `bug-13735b.php`, `precise-scope-select-from-args.php`,
`assign-in-array.php` の 4 groups。`array-closure-parameters.php` は contextual callback typing、
`template-argument-unconstrained-send.php` の差は generic inference 全般なので除外した。

両 worktree の `vendor` は同じ既存 dependency tree を copy し、各 worktree で
`composer dump-autoload --no-interaction` を実行して branch ごとの class map を再生成した。
全 suite は回していないため、結論は上記の source / history / targeted probes の範囲に限定する。

## 最終判断

- 「2.3.x で effect system が変わったか」: 変わっていない。
- 「副作用に伴う型事実の無効化が変わったか」: 変わった。static call / closure の
  reachability に応じて、保持と無効化を選ぶ footprint になった。
- 「式内の副作用の反映が変わったか」: 変わった。single-pass の stored result により、
  左から右の state mutation が後続 sub-expression と call resolution に反映される。
- effect-envelope port への影響: 公開構文の衝突はないが、implementation seam は全面的に
  2.3.x handler / `ArgsResult` / `ScopeOps` へ移して、label propagation と scope invalidation を
  別々に保つ必要がある。
